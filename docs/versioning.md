# 版本管理（第 2 阶段）

**工作区是版本库，酒馆是部署目标。** 修改、版本、标签都在软件这边的工作区（桌面版默认在程序目录下的 `workspace`，源码运行默认 `文档/TavernCellar`，均在酒馆数据目录之外）；
每个酒馆各自决定部署什么：**跟随最新**（工作区当前的内容），或**固定在某个版本**。两个酒馆之间不直接同步，
都经过工作区：一边的改动先取回成版本，再部署到另一边。

界面是一个简化的 git 图形页：未记录的修改、记录版本、标签、对比、推送。用户不需要懂 git；用 git 命令看到的是同一份历史，
用 git 打的标签（轻量或附注）也会出现在界面里。

代码：`companion/src/vcs/vcs.js`（仓库操作）、`companion/src/sync.js`（与同步的衔接、历史接口）、
`studio/src/screens/HistoryPage.vue`（历史页）。

## 1. 存储

- 伴侣程序第一次打开工作区时，如果还没有 `.git`，就创建仓库（默认分支 `main`），并写入 `.gitattributes`
  （`* -text`，不让 git 在 Windows 上改换行）。已有仓库则沿用它和当前分支。会用 jj 的用户可以执行
  `jj git init --colocate` 共用。
- `.cellar/`（同步状态、基准快照、冲突、备份）在 `.gitignore` 中，不进历史。项内的临时文件与编辑器备份
  （以 `.` 开头、`.tmp`、`~` 结尾）也不进历史，规则与读取资料项相同。
- 只有一个后端：isomorphic-git（纯 JS，用户无需安装 git）。没有做“检测到系统 git 就切换”：两套实现就是两条
  路径、两倍测试；仓库格式相同，用户照样可以在工作区里用 git / jj 命令。
- 判断文件有没有变不用 git 索引的缓存：isomorphic-git 只比较到整秒的修改时间，一秒内两次同样长度的修改
  （比如把“霜蚀 3”改成“霜蚀 4”）会被漏掉。伴侣程序自己按内容计算哈希，缓存只在文件写入至少 2 秒后才信任。
  git 索引仍会随之更新，所以 `git status` 与记录的版本一致。

## 2. 交互模型

| 概念 | 实现 |
|---|---|
| 草稿 `@` | 分支最新的提交，由 `refs/cellar/draft` 标记。文件变化后（去抖约 1.5 秒）用替换（amend）的方式更新：父提交不变，内容换成当前文件，历史里不会出现大量零碎提交。改动全部撤销时草稿自动消失 |
| 写说明 | 修改草稿的说明（`describe`），不结束草稿 |
| 记录版本 | 写说明并结束草稿（`commit`）；下次修改时开始新草稿。没有说明的版本显示为“未写说明” |
| 版本标签 | git 轻量标签。给草稿打标签等于检查点：先把草稿按当前文件结束为版本（保留它的说明），再给这个版本打标签 |
| 已部署指针 | `refs/cellar/deployed/<目标>/<项编号>`，指向该项最后一次与该酒馆一致时的版本。项编号是项路径 SHA-1 的前 20 位十六进制：长度固定，长中文名也不会让引用文件路径超过 Windows 上 git 的长度限制。旧的 `%XX` 编码命名在启动时自动改名 |
| 酒馆端的修改、取出、恢复 | 和手动编辑一样只进入草稿，不自动结束草稿、不另记版本（同 jj：只有用户记录版本或打标签才产生检查点）。代价：同一个草稿里分不出哪些是自己改的、哪些来自酒馆；需要分开时，先记录版本再取回 |

只替换同时满足“被 `refs/cellar/draft` 标记”和“位于分支最新处”的提交。用户自己用 git 提交了，下一次快照
就在其上开新草稿，绝不改写用户的提交。

## 3. 部署：跟随最新 / 固定版本

每个绑定（资料项 × 酒馆）处于两种状态之一，记在 `cellar.json` 的绑定上（`pin: "<版本编号>"`，没有就是跟随）。

| | 跟随最新（默认） | 固定在版本 V |
|---|---|---|
| 部署的内容 | 工作区当前的文件 | V 中该项的文件，工作区不动 |
| 工作区修改后 | 显示“本地有修改”；随时同步的绑定立即同步 | 不同步，状态仍是一致；另标“工作区已更新” |
| 「同步」「同步全部」「随时同步」 | 正常工作 | 跳过；单独同步时提示“已固定在 V，先改为跟随最新” |
| 酒馆里被修改 | 自动取回或按槽位合并（第 1 阶段规则） | 不动工作区，只标“酒馆里有修改”。用户选：**取回**（把酒馆在 V 之后的改动按槽位合并进工作区，记为「来自 <酒馆>」版本，绑定改为跟随）或**重新推送 V**（覆盖酒馆的改动） |

- **推送版本**：选一个版本（或标签）和一个酒馆，把这个版本里、绑定了该酒馆的项写过去（也可以只选其中几项）。
  版本是整个工作区的快照，Studio 历史页因此总是明确给出要推送的项：只看一项时是这一项，看全部时是这个版本修改过的项；
  不带项的 `cellar push <版本>` 才是“快照里全部绑定项”。
  写入仍用基准哈希复核：酒馆在上次一致后又被改过，就拒绝并报告，不会惄悄覆盖；用户确认后可以强制推送。
  成功后该绑定固定在这个版本，已部署指针指向它。版本中没有的项不动。
- **改为跟随最新**：去掉固定；此后按普通绑定处理（工作区与部署版本不同就是“本地有修改”，开着随时同步则立即同步）。
- **推送最新**不是单独的操作：就是跟随最新 + 同步。
- 「恢复成所选版本 <编号>」保留，用途是让工作区里的一项回到所选版本（不是对比的那个版本）、从那里继续写；它和推送是两件事。

固定绑定的同步状态：基准哈希与基准快照是推送时酒馆存下的版本 V。酒馆与它不同 = 酒馆里有修改；工作区与它不同
不算未同步。取回时正好用 V 作合并基准：工作区保留 V 之后自己的修改，酒馆在 V 之后的修改合并进来，两边改了同一处才是冲突。

## 4. 与同步的关系

- 同步判断仍由 `.cellar/state.json` 的基准哈希和 `.cellar/base/` 的基准快照负责（按槽位三方合并要用）。
  冲突处理期间基准会按槽位推进，这个快照不一定对应任何一个版本，所以不能用“已部署版本里的文件”代替它。
- 已部署指针记录每个酒馆里是哪个版本，不参与同步判断。设置时机：工作区与酒馆达成一致的每个地方（取出、同步、取回、
  合并后一致、绑定时内容相同），以及推送版本。同步一个还没记录的草稿时，指针指向当时的草稿；之后草稿再被替换，
  那个提交仍由指针保留。历史页把它显示在后来的版本上：只改了说明时就是该版本，内容又变过则标为“较早状态”。
- 解除绑定时删除对应的指针（固定随绑定一起消失）。
- 第 1 阶段的工作区升级：第一次打开时生成版本「开始版本记录」，当时已同步的绑定都指向它。

## 5. 对比

两个版本中同一项的文件各自用编解码器合成数据，再按冲突页同一套槽位和名称逐项比较（`POST /api/history/diff`、
`cellar diff`）。字符串只差换行符（例如酒馆编辑器保存成了 CRLF）时标出“只有换行符不同”。

## 6. 接口

| HTTP（`POST`） | 命令行 | 作用 |
|---|---|---|
| `/api/history {path?, limit?}` | `cellar log [项] [--limit N]` | 草稿、版本列表（新到旧，可按项筛选）、各绑定的已部署版本 |
| `/api/history/describe {message}` | `cellar describe "说明"` | 给草稿写说明 |
| `/api/history/commit {message}` | `cellar commit "说明"` | 记录版本；没有新修改时报错 |
| `/api/history/tag {name, rev?}` | `cellar tag <名称> [版本]` | 打标签（默认最新版本） |
| `/api/history/diff {from, to?, path?}` | `cellar diff <A> [B] [项]` | 按字段对比 |
| `/api/history/restore {rev, path}` | `cellar restore <版本> <项>` | 把工作区里的一项恢复到某版本 |
| `/api/item/undo {path}`、`/api/item/redo {path}` | — | 撤回 / 取消撤回这一项的上一次写入（§6.1） |
| `/api/item/revert {path}` | — | 撤销当前的修改：这一项恢复成最近一次记录的版本 |
| `GET /api/history/storage` | — | 历史占用（字节、文件数、可清理的部分、上次压缩） |
| `/api/history/compact {}` | — | 压缩历史（§7.1） |
| `/api/push {rev, target, paths?, force?}` | `cellar push <版本> [项...] --target <酒馆> [--force]` | 把版本推送到一个酒馆并固定；结果按项列出 |
| `/api/follow {path, target?}` | `cellar follow <项> [--target <酒馆>]` | 改为跟随最新 |

版本可以写完整编号、前几位、标签名或 `HEAD`。`GET /api/status` 的每个绑定带 `deployed`；固定的绑定另带
`pinned: {rev, name, ahead}`（`name` 是该版本的标签或编号前 8 位，`ahead` 表示工作区已有更新）。顶层带 `draft`
（草稿编号与改动的项），Studio 的检查栏、同步矩阵和状态栏用它们显示。

### 6.1 撤回

- 伴侣程序在内存里为每一项记撤回步骤（最多 30 步，重启或切换工作区清空，不进版本历史）：经 Studio 的写入（字段、条目、文件）、恢复、
  撤销当前的修改都记一步；1.5 秒内连续的自动保存合并成一步。撤回 / 取消撤回本身也走同一条写入路径（哈希防覆盖，草稿照常记录）。
- 这一项在别处被改过（外部编辑器、取回、同步合并）时，撤回步骤作废，撤回会报冲突而不是覆盖。
- 「撤销当前的修改」= 把这一项恢复到草稿的父版本（最近一次记录的版本）；该项不在草稿中时不可用。在最近一次记录之后才取出 / 新建的项
  （包括移除后重新取出的），恢复成取出 / 新建时的样子：取出与新建时把当时的草稿快照记在 `refs/cellar/origin/<项编号>`，
  只在它属于当前草稿（父版本就是最近一次记录的版本）时使用；移除该项时删除这个引用。
- `GET /api/status` 的每项带 `edits: {undo, redo}`。

## 7. 已知限制

- 每次快照都要遍历整个工作区（有缓存，只重新读取变过的文件；忽略规则在内存中匹配）。2750 个文件的工作区：冷启动约 1 秒，之后约 70 毫秒。
- 用户同时用 git 命令行操作同一个仓库时，以伴侣程序看到的分支最新提交为准；不处理合并、变基中的仓库状态
  （HEAD 游离时跳过快照并记日志）。
- 作者固定为 `TavernCellar <cellar@localhost>`，不读取用户的 git 配置。

### 7.1 压缩历史

- 草稿每次快照都会改写，被替换掉的中间状态（以及只有它们用到的文件内容）留在仓库里成为“不再使用的对象”。
  所有引用（分支、标签、草稿、`deployed` / `origin` 指针、HEAD）能走到的提交、目录与文件都保留，其余的就是可清理的部分。
- 「压缩历史」（设置 → 版本历史，或 `POST /api/history/compact`）：先把当前文件记入草稿，删除 10 分钟以前就不再使用的对象，
  再把仍需要的全部写进一个 pack（先建好索引再删旧文件，中断最多留下重复），之后改为读 pack。版本、标签、草稿、部署记录都不变。
- 自动清理（默认开）：启动 1 分钟后与之后每 12 小时检查一次。历史超过设定大小（20 / **50** / 100 / 200 / 500 MB）时压缩，
  压缩后仍超过的要再增长 20% 才再压缩；否则只删除超过设定天数（7 / 14 / **30** / 60 / 90 天）就不再使用的对象，不打包。
  上次压缩记在 `.cellar/state.json` 的 `history.compacted`。
- 快照只写新内容：文件先算哈希、目录先算编号，已有的对象（包括 pack 里的）不再写成散文件，否则每次重启都会把打包过的内容重新散开。
